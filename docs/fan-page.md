## 一、这是什么

用户要求：「做一个粉丝向的网页，在 ART 页面 … 下方做一个去往这个网站的按钮。页面是一个针对绘画粉丝的 single page 网站（需要有中文和英文切换按钮，并且该界面只有一个风格而不是分 light / dark mode），主题和风格参考 `下载/粉色参考` 里的素材（明日方舟「逐影集趣」活动）」。

- 内容：**RrSuika Studio 自己的画**（用户选定），不是游戏活动页。
- 视觉：参考素材的**粉主色 + 高饱和深蓝**，以及那套印刷语汇。
- 结构：单页、独立整页、ART 页按钮**新标签打开**。

## 二、只有一套主题（用户明确要求）

⚠️ 站点在 `<html>` 上有 `data-theme`，导航和页脚都吃它。这个页面**不去禁用主题**，而是在 `.fan-root` 上把站点 token 覆盖掉：

```css
.fan-root {
  --bg: var(--fan-cream);
  --text: var(--fan-ink);
  …
}
```

主题属性照旧存在、切主题也不会坏，只是这个页面怎么看都一样。实测（CDP）：`localStorage` 里存 `light` 或 `dark`，`.fan-root` 的 `color` 与 `.fan-title` 的 `color` **逐字相同**。

⚠️ **没有覆盖 `--accent`**：它还喂着 skip-link 和焦点环，而那些不是这个页面画的。页面自己画的东西一律显式给色。

## 三、hero：戴王冠的云是**画出来的**

⚠️ 第一版用嵌套的 `border-radius: 50%` + `box-shadow` 环想做云，结果渲染成**四个同心圆环**——圆角方盒只能做环，做不出波浪边。现在是**一条 SVG path**：波浪的上沿 + 波浪的下沿，关于 x=120 对称，`stroke-linejoin: round` 让每个凸起是圆的，粉色外描边 + 白色内描边同源，所以读起来是"印出来的一朵云"。

⚠️ 王冠是绝对定位在 `.hero-blob` 的**盒子**中心，而云的 path 在 viewBox 里左右上下都有余量，**视觉中心不等于盒子中心**（实测王冠偏右下）。现在按 `left: 47.5%; top: 40%` 对到云身上。改云的 path 就要重新对一次。

## 四、没有主站导航与页脚

用户选的是「独立整页，不套主站导航」。页头页脚是主站的**深色表面**，而页脚自己的作用域规则优先级高过这个页面能写的任何东西——实测 `body:has([data-fan]) .footer { background: … }` 写进去了（构建产物里能查到），渲染出来仍是黑的一条。与其继续对打，按 brief 直接**不显示**：

```css
:global(body:has([data-fan]) .site-content > header),
:global(body:has([data-fan]) .footer), … { display: none !important; }
```

⚠️ 用 `display: none` 而不是 `visibility: hidden`：后者留着高度，页面顶部会有一条死带。页面自己帶 `← 回到工作室` 和语言切换，功能不缺。

⚠️ **选择器必须是 `.site-content > header`，不能是裸的 `header`。** 这个页面自己的 hero 也是 `<header>`，裸选择器会把它一起删掉——实测整块 hero（云、王冠、字标、两个 CTA）全部消失，顶栏下面直接接模块 01，整页看起来只是「少了点什么」。**抓到它的是全页截图，不是任何断言**：当时所有断言都是绿的。删主站外框的规则，一律钉到 `.site-content` 那层。

⚠️ 这些是这个文件里**仅有**的 `:global` 规则，且每条都套在 `[data-fan]` 下，不可能漏到别的页面。

## 四之二、右侧蓝色页面导轨

站点**故意藏掉滚动条**，这一页照办。但页面有 4000+ px，总得有人告诉你走到哪了，于是位置是**画出来**的：`.fan-rail` 一条 4px 的蓝轨（蓝 = 这一页的信号色），填充部分带一层粉色光晕，`--fan-read`（0→1）由页面脚本驱动。

- 装饰件：`aria-hidden="true"` + `pointer-events: none`，不参与命中测试、不进朗读顺序。
- 驱动是 **rAF 节流**，而且只写**一个自定义属性**：填充高度是 `calc(var(--fan-read) * 100%)`，滚动时浏览器不做布局计算。分母必须是 `scrollHeight - innerHeight`（真正可滚的距离），用 `scrollHeight` 的话长页面永远只走到一半。
- 位置 fixed，`top: 140px / bottom: 66px`，让开顶部两条栏和页脚。

⚠️ **`.fan-root > *:not(...)` 那条规则又吃了一个定位。** 它给每个直接子元素写 `position: relative`，而且排在后面、同样 0-2-0 优先级，于是 `fixed` 被顶掉：实测导轨 `position: fixed` → 计算值 `relative`，`left` 变成 **-14px**（跑到屏幕左外面去了）。现在排除列表是 `:not(.fan-modules, .fan-rail)`——**任何自己管定位的 `.fan-root` 直接子元素都必须写进这个列表。这是同一条规则第二次吃掉定位（第一次是吸顶模块条）。**

⚠️ **不要用计算样式验证吸顶/固定定位。** `.fan-modules` 那次的教训：规则明明写着 `position: sticky`，`getComputedStyle().position` 却报 `relative`（被上面那条规则顶掉），而修好之后**仍然报 `relative`**（它是 flex 子项 + 祖先 `overflow` 的结果）。唯一有意义的判据是**滚动之后量位置**：滚 1400px 后 `getBoundingClientRect().top` 应等于 0。

## 五、档案排的循环：份数由视口决定，周期由 DOM 量

⚠️ 两处都是从 `/art` 抄来的，**在这里都是错的**：

1. **`copies`**。`/art` 用 `max(3, ceil(12 / n))`，在这个页面等于把整套作品画三遍：最长那排实测 **27 张卡 / 5517px**，而内容区只有 1180px，于是同一批九张画在屏幕上重复三次。现在按视口算：`max(2, ceil(ROW_VIEW_W / (n × ROW_ITEM_W)) + 1)`，实测 9 张的画廊降到 2 份（18 张卡）。
2. **周期**。`scrollWidth / copies` 是**错的**：track 是带 `gap` 的 flex 行，最后一张卡后面没有 gap，这个除法会短一点点，越滚越偏。现在 `measurePeriod()` 直接量 **相隔 `unique` 张的两张卡的 `offsetLeft` 差**——那正好是一圈，`resize` 时重量（卡宽会被媒体查询改）。

滚动速度 0.22–0.34 px/帧、每排交替方向、hover 暂停、可拖拽（`pointerdown` 接管、5px 位移内才算点击），这些和 `/art` 的交互语言一致。

## 六、ART 页的入口按钮

`src/components/FanCta.astro`，三个 `/art` 页共用。

- ⚠️ **它是组件而不是三段复制**：三个 `/art` 页是三个**独立文件、各自一个 `<style>` 块**，同一段 markup 抄三遍就是同一段 CSS 抄三遍——而这三个页面恰好是"三语之间悄悄跑偏最难发现"的地方。
- ⚠️ **`isolation: isolate`**：hover 的填充是 `z-index: -1`，没有它就会跑到页面背后去（tag chip 踩过的同一个坑）。
- 配色**故意不是站点琥珀**：它是页面上唯一一个"离开本站"的控件，穿的是目的地的粉。hover 手势沿用站点的（强调色从下往上滑过文字），所以它仍然属于这一页。
- `target="_blank" rel="noopener"`：粉丝页有自己的返回，把访客从画廊带走会丢掉他在一个"以浏览为目的"的页面上的滚动位置。

### 云不完整的真正原因

旧 path 没有闭合：最后一段扫描终点没回到起点，底部左侧留了一条**直线弦**，读起来就是“云不完整”。现在是一条闭合路径，每段都是 `a r r 0 0 1 dx 0`（因此必定是半圆），外轮廓用 `fill-rule: evenodd` 把白心挖出来，同时消掉了旧底部弧画出的海鸥缺口。

⚠️ **viewBox 必须保持正方（0 0 242 242）。** 我把它收紧到轮廓外接矩形（25 50 192 132）看着像整理，实际把云**拉批**：`meet` 会先填满宽度，于是 290px 宽的云只剩 199px 高（宽高比 1.34）。空白条改用布局解决：`.hero-blob { margin-bottom: -96px }`（轮廓在 242 盒子里只占上部约 175px）。

## 十、第三轮：换名、中文画名、催更按钮

**英文结尾语**：`Mercy, boss — I am drawing already.` 是「大王饶命，小的已经在画了」的直译，读起来是坏英语。笑点是一个夸张的求饶，英语里有原生语域：**`Have mercy — I'm drawing as fast as I can!`** —— 同一个笑话，不是译文。

**水果之前为什么有的很丑：它们根本不是水果，是水果的碎片。**

`FRUIT` 原来是一张**扁平**的路径表，于是两色水果就是**两条记录** —— 草莓的叶子和果肉是两条、椰子的壳和眼是两条、西瓜的皮和瓤是两条。而生成器**只抽一条**，所以三分之一的玩具是：一个没有草莓的绿星星、三颗没有椰子的棕色圆点、一片没有瓜皮的红色月牙。**扁平表无法表达「这三条路径是同一个草莓」。**

现在一条记录 = 一个水果，带 `parts` 列表，渲染器把它们全部放进同一个 `<svg>`。实测 300 次抽取里 **12 种水果全部出现，0 个碎片**。

⚠️ **这个 bug 是「把每一个拿出来看」才发现的。** 成堆的玩具在屏幕上看着只是「有点丑」，把它们单独排成一行就立刻暴露了 —— 一排绿星星和棕色圆点，一眼就知道那不是水果。**判断图标好不好看，要脱离堆叠看单片。**

同时补了三个你要的：**蓝莓**（果实 + 五点花萼）、**芒果**（斜椭圆 + 果梗）、**葡萄**（r=13、圆心间距 20，之前 r=14、间距 22 让相邻两颗粘成了一个长条）。重画了四个读不出来的：草莓（肩部 + 尖头 + 五片叶）、椰子（切开的样子，壳 + 露出的白肉 + 三个眼，之前是一个棕圆里三个深圆 = 漂浮的点）、西瓜（瓜皮现在是 10px 的边，果肉占大部分）、梨（腰部收窄）。
### 第十一轮：椰子、尺寸变化、梨和菠萝重画、轻一点的玩笑

**椰子**：切开那版把三个眼放在了**白肉上**，读起来是一张脸。访客要的是「整体棕色 + 三个点」，照做。

**尺寸**：每个玩具原来是同一个 76px 盒子，蓝莓和西瓜一样大，一堆看上去像网格。现在每个水果带一个 `scale`，实测 12 种里 **7 档不同尺寸，最大最小差 20px 以上**。

⚠️ **缩放走 SVG 的盒子，不走 `transform`。** SVG 的 `transform-origin` 默认是 `0 0` 而不是中心，而且玩具自己的 `transform` **每帧被求解器重写** —— 放在 `transform` 上会互相打架。把 svg 的 `width/height` 设成百分比、再用负 margin 居中，元素的**布局盒子仍然是 76×76**，所以碰撞半径和求解器完全不受影响，只有画面溢出。

**梨**：`a27 27 0 0 0 54 0` 是一个**半圆** —— 所谓「果身」是半圆上面接一根脖子，也就是一个钥匙孔。现在是真正的梨形轮廓（顶部窄、底部圆），用三次曲线画。

**菠萝**：`M34 48 h52` 给出一个**平的 52px 顶**，`c0 24` 从两端垂直下落，所以果身是一个圆角矩形。现在中间鼓起、上下收窄，冠部改成五片尖叶而不是五条直线。

**芒果**：原来是整套里最小的一个 —— 路径放大，同时给了最大的 `scale`（1.14）。

### 第十二轮：水果的手感 —— 位置求解器

访客：「水果多了以后，从上面掉下来的水果会导致下面所有的水果都动起来，感觉都轻飘飘的，没有手感。」

**根因在 Verlet 积分器的语义上。** `px`/`py` 是**上一帧位置**，所以 `v = x − px` —— **改动 `px` 就是改动速度**。原来的分离步骤把 `x` 和 `px` 一起推：

```js
a.x -= pushX;  a.px -= pushX;   // 位置推了，速度没变
```

方向上是「不注入速度」，但它在**每一对有重叠的物体上每帧都跑**，而推力正比于重叠量 —— 于是堆叠里相邻两颗**来回传递速度**，而没有任何机制把它耗掉。一颗水果时看不出来；四十颗的时候，一次落地会顺着整堆传出去，就是「轻飘飘」。

**修法是位置求解器的标准做法：接触修正只改位置。** `prev` 不动，修正就不产生速度。在此之上：

| 参数 | 值 | 作用 |
| --- | --- | --- |
| `SOLVER_PASSES` | 2 | 一遍分离会让三层高的堆还有重叠，残留量就是下一帧的抖动 |
| `CONTACT_REST` | 0.72 | 每次接触都吃掉一点法向速度，落地被吸收而不是传下去（先取 0.84，回弹仍然偏「弹」；0.72 才落地即停） |
| `CONTACT_FRICTION` | 0.3 | 切向损耗 —— 没有它，一堆水果像在冰上滑开 |
| `GROUND_FRICTION` | 0.34 | 地面上的切向损耗 |
| `WAKE_OVERLAP` / `WAKE_SPEED` | 0.25 / 0.25 | 见下 |
| `CONTACT_DAMP` | 0.86 | **接触期间的速度阻尼 —— 这条不能省** |
| `CORRECTION_CAP` | 2px | 单次分离的上限，见下 |

⚠️ **判据：睡眠计数器永远到不了阈值。** 分离循环原来每次接触都写 `t.asleep = 0`，而**静止的接触每帧仍然有零点几像素的重叠** —— 于是没有任何东西会睡着，求解器一直在重新分离一个**已经分离好的**堆。实测 24 颗静止时总位移 **236px**，一次掉落把 **1974px** 的位移推进整堆。现在接触只在**真有重叠**（>0.25px）或**真有相对速度**（>0.25px/帧）时才唤醒，静止的堆睡下去，求解器整个停下来。

⚠️ **地面不能要求「有接触」才算醒着。** 躺在地上的那颗**没有任何配对**，原来的 `asleep` 逻辑会把它永远算作活跃；现在地面只负责阻止计数器增长，判定交给各自的静止测试。

**实测判据（按每颗算，不是总数）**：静止时 **< 18px/颗**（1.8 秒），掉落一次后整堆位移 **< 静止值 × 6 + 400**，2.5 秒后再测漂移 **< 8px/颗**，没有一颗穿过地面。
⚠️ **只修位置还不够，接触中必须有损耗通道。** 位置修正不再注入速度之后，残留的是一个**低速爬行**：实测 24 颗静止时每颗 1.8 秒走 **21.6px**，这个量**永远跨不过睡眠阈值**，所以堆会一直「呼吸」。`CONTACT_DAMP` 就是那条缺失的损耗通道。

⚠️ **分离量必须封顶。** 推力正比于重叠量，所以一颗高速水果**嵌进**另一颗时会产生一次 20px 的单帧猛推 —— 那正是把已经静止的整堆**打飞**的原因。封在 2px/次之后，深重叠在几帧内解开，这也更接近真实刚体。

**最终实测**（每颗，不是总数）：静止 **19.7px / 1.8s**（≈0.18px/帧，76px 的玩具上看不见），掉落一次后整堆位移显著低于静止值的 6 倍，2.5 秒后漂移回到静止量级，没有一颗穿过地面。

### 第十三轮：去掉菠萝、英文结尾语改词

访客：「删掉菠萝，然后 Say hello any time 改成 Feel free to chat」。

**菠萝**：`FRUIT` 从 **12 条变 11 条**（苹果、梨、草莓、水蜜桃、樱桃、香蕉、西瓜、葡萄、蓝莓、芒果、椰子）。删的理由不是画得不好，是**它在堆里读不出是菠萝**：桶身是这一套里最窄的形，冠部又是最宽的，堆起来只剩一团绿色尖角顶在一个小盆上。

⚠️ 一条记录 = 一个水果，所以删掉整条记录就是删掉这个水果；`spawn` 取的是 `FRUIT[Math.floor(Math.random() * FRUIT.length)]`，条数一改抽取自然跟着改，别处不需要动。

**结尾语**：`commissions.note` 的英文从 `Say hello any time — questions about drawing are welcome too.` 改成 `Feel free to chat — questions about drawing are welcome too.`。中文那句（「欢迎沟通，绘画上有问题也可以问~」）本来就是「随便聊」的口气，不动。

**复验**：`输入/_scratch/final-check.mjs` 里的断言 `uniqFruits >= 12` 必须跟着改成 `>= 11` —— **这个数字是代码的镜像，删水果不一起改，测量就会永远 FAIL**。重跑：`final-check.mjs` **6/6 PASS**（11 种全部出现、0 个碎片、多部件完整、无高光笔、玩笑语气、尺寸不一）；`plate-big.mjs` 出图 **11 种、无菠萝**，逐个确认没有碎片。

⚠️ 判据还是第十二轮那条：**新水果必须单独排成一行看**。这次也是先出大图确认 11 个都完整，再回头改断言。
## 十二、动态背景 — Mosaic Lens（`src/components/FanMosaic.astro`）

访客要求：「我希望粉丝页的背景是这样的动态效果，同时要贴合我给的那个粉色文件夹的参考」，并附上了自己的一份 React + WebGL2 组件（Originkit 的「Mosaic Lens」）。

### 它是什么

两趟渲染：

1. **field**：一个 74 层的折叠迭代（`rot/shrink/shear` + 两次 warp），每层往同一个点 `(OFFSET,0)` 打一束 `GLOW/(dot(q,q)+SOFT)` 的辉光，按 `mix(uC1,uC2,k)` 上色 —— 结果是一张浮点纹理，画进 FBO。
2. **finish**：把这张纹理**磨砂化**——模糊半径随指针距离分 4 档收窄（`tier = floor(min(w*5,4))`），指针正下方 `tier >= TIERS` 直接全分辨率采样，也就是「镜头在起雾的玻璃上擦出一块清亮」。最后按底色亮度在「暗底加光」和「纸面提亮」两种混合之间插值，再叠上印刷网点，加一层 ±0.5/255 的抖动。

### 第二轮：马赛克 → 磨砂玻璃（访客要求）

访客第一版看完的反馈是两条：「背景有点类似磨砂玻璃的朦胧感」，以及「背景的肌理和这个新特效没有很好融入」。

第一条改的是 finish 的取样方式。原版的马赛克是**方格平均**：`floor(frag/cell)` 取格心，再在 ±0.25 格取四个点平均 —— 那是**像素画**，硬边、轴向、有网格。放在粉色的柔光上，它读起来像**罩在页面上的一层纱窗**，不像页面自己的表面。改成：

1. **Vogel 圆盘**（黄金角螺旋 `a = fi * 2.39996323`）取样，各向同性：没有方向、没有格子、没有块边，也不会和网点打架；
2. **每像素自己的随机折射**：`j = (hash(frag) - 0.5) * grain`，加到每个取样点上。这才是磨砂玻璃**物理上**在做的事 —— 每一条光线被折射的角度都略有不同。只做模糊得到的是「一张糊了的图」，加上这个每像素折射才读成**霜面**。半径和折射量都乘在 `cell` 上，所以镜头把 `cell` 收到 0 时，雾和霜一起被擦干净。

第二条改的是「肌理」的来源。原来那层印刷网点是 `.fan-root::before` 的 CSS 层，**盖在**画布上面 —— 两个不同来源、不同相位的纹理叠在一起，就是「不融入」。现在**网点由着色器自己画**（`dots()`，同样的 7px 间距、同样的 `--fan-dot` 颜色），而且采样位置被同一个每像素折射**推开**：网点属于玻璃本身，雾厚的地方它散开成颗粒，镜头擦过的地方它回到整齐的网点。

⚠️ **两套网点必须二选一。** 着色器接管表面时会写 `data-mosaic="on"`，CSS 那条 `.fan-root[data-mosaic="on"]::before { opacity: 0 }` 让 CSS 那层退场 —— 两个相位不同的网点叠在一起会**产生莫尔纹**，比任何一个单独看都糟。掉上下文时属性被移除，CSS 那一套（底色 + 天空 + 网点）就重新成为可见的页面。

### 第三轮：把背景对比压下来，为了正文好读

访客反馈：「背景的动画对比稍微弱一点，这样正文容易阅读。」

⚠️ **`gain` 不是这个旋钮。** 先把 `GAIN` 从 0.3 降到 0.2、天空从 0.4 降到 0.3，实测纸面最暗那一块只从 `rgb(248,125,189)` 动到 `rgb(248,133,189)` —— **不到 8/255**。原因是 `gain` 作用在色调曲线**之前**，而曲线和 `pow(col, vec3(0.85,0.92,0.98))` 这一下提亮又把范围还回来了。

真正的旋钮是 `--fan-mosaic-contrast`：把场相对纸面的**偏离量**整体缩放 —— `L = uBg + (L - uBg) * uContrast`。这是对「访客实际看到的对比」直接下手，而且因为霜的颗粒是高频率的，压完对比之后**肌理还在**。

实测取 0.6（1440×950，跨一整个呼吸周期，5×4 网格采样，内容是隐藏的）：

| | contrast 1（原样） | contrast 0.6 |
| --- | --- | --- |
| 最暗的一块纸面 | `rgb(248,133,189)` | `rgb(247,172,202)` |
| `--fan-ink` | 7.7–8.4 : 1 | **9.9–10.4 : 1** |
| `--fan-ink-soft` | 3.6–3.9 : 1 | **4.6–4.9 : 1** |

⚠️ `--fan-ink-soft` 到这一步才**第一次过 AA**（4.5:1）。它之前一直不达标：改这个背景之前是 3.22:1（hero 一片实心 `--fan-pink`），加了马赛克之后 3.44:1。也就是说这条抱怨指出的不只是「背景太强」，还有一个**从改版前就存在**的小字对比度问题。

⚠️ **这只是换了渲染方式的「同一张画」**：field 那一趟的着色器逐字照搬（除了 `GAIN` 改成 uniform、见下），React 换成这个仓库的裸 TS，`props` 换成 CSS 自定义属性。

### 怎么调（全部在 `.fan-root` 上，`FanMosaic.astro` 通过 `getComputedStyle` 读）

| 属性 | 值 | 说明 |
| --- | --- | --- |
| `--fan-mosaic-bg` | `#fff0ec` | 纸面底色，**必须和 `.fan-root` 的 cream 一致**，否则 hero 会读成一个矩形 |
| `--fan-mosaic-c1` / `-c2` | `#ff6fa8` / `#f5308a` | 辉光的两端颜色，直接用页面自己的粉 |
| `--fan-mosaic-gain` | `0.2` | 场在色调曲线**之前**的曝光。只影响颜色浓淡，**不是**控制可读性的旋钮（见第三轮） |
| `--fan-mosaic-contrast` | `0.6` | **可读性旋钮**：`1` = 着色器原样，越小则场相对纸面的偏离被压得越平 |
| `--fan-mosaic-frost` | `2` | 磨砂的模糊半径，按 `tile` 的倍数算（2 × 18 ≈ 36px） |
| `--fan-mosaic-grain` | `1.4` | 每像素折射量（CSS px）。**这个数决定它像霜面还是像糊图** |
| `--fan-mosaic-dot` | `0.26` | 印刷网点的强度（CSS 那层是 rgba 0.16 × opacity 0.5 ≈ 0.08） |
| `--fan-mosaic-tile` | `18` | 磨砂的基准格子（CSS px）：镜头分档和模糊半径都由它派生 |
| `--fan-mosaic-size` | `70` | 视野缩放，越小特征越小、越有细节 |
| `--fan-mosaic-reach` | `300` | 镜头半径（CSS px） |
| `--fan-mosaic-hover` | `100` | 镜头强度 |
| `--fan-mosaic-speed` / `-angle` | `100` / `0` | 时钟速度 / 视野旋转 |
| `--fan-sky-opacity` | `0.3` | hero 那层粉色天空压在多厚的玻璃上（见下） |

⚠️ **`GAIN` 是唯一必须改的默认值。** 访客原版把它写死在着色器里（`0.54`），那是**对着近黑底**调的：finish 那一趟在浅底上走的是 `bg*(1-strength) + L*0.96`，同一份曝光放到奶油底上会把所有中间调压成一片死粉——第一次实测出来就是一整屏玫红，字全糊在里面。它现在是 uniform，页面给 `0.2`。

⚠️ **浅底上 `uPaper` 必然是 1。** `uPaper = clamp((bgLum-0.35)/0.3)`，奶油底 `bgLum≈0.94` → 1，也就是永远走「纸面提亮」那条路径（另一条在浅底上等于没有效果：`dark = bg + L*(1-bg) ≈ 0.94 + 0.06L`）。

### hero 的粉色天空为什么是一个**独立元素**

`.fan-root` 原来的背景是四层渐变（粉色天空 + 两团侧光 + 奶油竖渐变）。马赛克画布是 `position: fixed; z-index: -1` 的**子元素**，而子元素永远画在父元素背景**之上** —— 所以那四层会整片被盖掉。

于是把三团粉色渐变搬进 `.fan-sky`（一个 `position: absolute; z-index: -1` 的兄弟元素，高度 1400px = 老那道 `ellipse 120% 52% at 50% -6%` 在整页盒子里的实际射程），`.fan-root` 只留奶油底色。好处是：

- WebGL 版和 fallback 版**看起来一样**（`.fan-sky` 与 WebGL 无关，永远在画）；
- `--fan-sky-opacity` 成了一个旋钮：1 = 马赛克被完全盖住（就是改之前的页面），0 = 马赛克全裸，0.45 是现在这版。

⚠️ `.fan-sky` 和 `.fan-mosaic` **都必须写进 `.fan-root > *:not(...)` 白名单**（现在是第四个和第五个）。不写的话那条 `.fan-root > *` 会把它们改成 `position: relative; z-index: 1`：画布会变成页面顶部一条 100vh 的带子并盖住内容，天空会变成 1400px 高的占位块把整页往下顶。

⚠️ `.fan-root` 加了 `isolation: isolate`。**负 z-index 的子元素只在父元素是 stacking context 时才画在父元素背景之上**；不加这一条，画布会往上跑到最近的 stacking context，最后画在 `.fan-root` 不透明底色**下面** —— 一整页奶油、着色器在跑、控制台一个字都没有。

### 三处「量出来才发现」的东西

⚠️ **`gl.finish()` 在这里不等待。** 第一版做了一个 `bench()`：用 `gl.finish()` 圈住 30 次 field pass 计时，报回来 **0.0025ms**（200 次也这个数）—— 342k 像素 × 74 层不可能。ANGLE/WARP 下 `finish()` 不等脏活，这个探针是在撒谎，所以**删掉了**，改成量「同页面、同条件下把循环 pause 掉前后」的帧间隔（`__fanMosaic.pause()/resume()`）。

⚠️ **画布缓冲会被量成「整页高」。** `measure()` 原来直接读 wrapper 的 `offsetHeight`。wrapper 是 `position: fixed; inset: 0`，但它自己的样式表是**另一个文件**，而 `boot()` 可能跑在那张表生效之前 —— 实测在 reduced-motion 那次加载里读回来 **1440×3935**（整个文档高），第一帧就画进了 4 倍像素的缓冲里。现在**夹到视口**（`min(offsetHeight, documentElement.clientHeight)`），语义上也更对：这块东西的职责就是视口。

⚠️ **field 那一趟是节流的，finish 不是。** field 24fps、finish 每帧。field 自己的时钟是 `uTime*0.49`、呼吸周期约 8.5s，24Hz 看不出来；而马赛克格子和镜头是眼睛真正在追的东西，它们保持显示帧率。另外三个上限各有理由：`MAX_DPR = 1.5`（不是原版的 2）、field 缓冲长边夹到 `1400` 设备像素（反正输出是 18px 的方块，低于格子尺寸的细节本来也看不见）、`FIELD_MAX_SIDE` 让 2560px 的窗口不会比 1280px 的贵四倍。

## 追加（2026-09-28 之十六）：点阵「不是全部都是圆点，有的很混乱」

访客：「目前背景的点阵图有点问题，你检查一下，他不是全部都是圆点，有的是很混乱的，你可以截图看看问题。」

**放大 4 倍一看就清楚了：那不是圆点，是一格一格的「小箭头」。** 每个点都被剪成了同一个方向的月牙／人字形。

### 根因：把「每个点抖一下」写成了「每个像素抖一下」

我给网点加过一句「让颗粒跟着霜面散开」（那是上一轮「肌理要和新背景融合」的要求），写法是：

```glsl
col = mix(col, uDotCol, dots(frag + j * 2.0) * uDot);   // ← 错的
```

`j` 是**逐像素**的折射量（±1.4px）。把 7px 周期的**网格查表**按像素位移，得到的不是「点散开了」，而是**每个点被剪切** —— 相邻像素取到点内不同位置，形状就歪了；而哈希在局部是平滑的，于是所有点朝同一个方向歪，看起来就是一排排小箭头。

**修法：位移必须是「每个点」的，不是「每个像素」的。**

```glsl
vec2 cell = floor(p / uDotPitch);          // 先取格号
vec2 g = fract(p / uDotPitch) - 0.5;       // 再取格内坐标
float d = 1.0 - smoothstep(0.02, 0.3, length(g));   // 从圆心开始的软坡
return d * (0.85 + 0.3 * cellHash(cell));           // 每点的强弱
```

⚠️ **哈希必须吃「格号」，而且不能用 `ign()`。** `ign()` 是它参数的**线性函数**，喂整数格号会返回**条带**而不是噪声 —— 第一版用 `ign(cell, …)` 做逐点偏移和强弱，实测点沿着对角线成串地歪。换成格子哈希 `fract(sin(dot(c, vec2(127.1, 311.7))) * 43758.5453123)` 才是噪声。

⚠️ **不要加「半格偏移」。** `gl_FragCoord` 本来就采的是**像素中心**（`i+0.5`），所以 `fract(p/pitch) == 0.5` 正好落在像素中心上；我一度加了半格想让点更「正」，结果把它挪到**像素角**上，2×2 全值块 + 角溢出，反而更像十字。两种都拍过 4 倍图对比。

### 一个物理事实：7px 周期上的点**不可能圆**

一个点在 7px 周期里只有约 **3px** 大。3px 的圆在像素网格上必然栅格化成「中心一格亮 + 四邻 74% + 对角接近 0」——**那就是一个加号**。CSS 回退层（`radial-gradient(… 1px, transparent 1.2px)`）在同样的周期上画出来是同一个形状，访客对那一层没有意见。

所以顺手把它做成了可调的：**`--fan-mosaic-dot-pitch`（默认 7）**，半径按周期取比例，调大周期 = 点更大更圆、屏幕更粗。要「明显是圆点」就往 10–12 调。

### 顺手对齐的两件事

- 网点强度 `0.26 → 0.16`（CSS 那层的等效值是 0.08），逐点强弱从 0.6–1.4× 收到 **0.85–1.15×** —— 「有的深有的浅」本身也会读成「乱」。
- 4 倍截图脚本 `dots-zoom.mjs` 会**同时拍着色器版和 CSS 回退版**：⚠️ 4 倍图是**放大的位图**（画布仍按 dpr 渲染），单独看没有意义，只有两版并排才有判据。

### 三、水果改成捏捏乐的手感

访客：「水果做的 Q 弹一点，比如落地会弹一下，现在感觉太重了。参考捏捏乐那种 Q 弹的感觉。」

**① 地面原来根本不会弹。** 旧代码 `t.py = t.y - vn * 0.2` 保留的是**向下**的速度：落地 → 钳位 → 再往下蹭 20% → 再钳位 —— 一记闷响，没有回弹。恢复系数要把上一帧位置挪到**地面上方**才有反向速度，所以符号是 `+`：

```js
if (vn > GROUND_BOUNCE_MIN) t.py = t.y + vn * GROUND_BOUNCE;  // 0.62：一次明显的弹跳（§二十二）
else                        t.py = t.y - vn * GROUND_REST;    // 0.2：就地吃掉，睡着
```

⚠️ **没有阈值的恢复系数会让重力永远弹下去。** 静止的一颗每帧被重力压进地面 0.72px，0.42 的恢复系数把它变成 0.3px 的回弹，下一帧再落下 —— 永久抖动。实测没有阈值时静止堆每颗 1.8 秒走 **134.6px**（有阈值时 ~26px）。`GROUND_BOUNCE_MIN = 4.5`：从 14px 以上落下才弹，静止接触一律就地吃掉。

**② 挤压回弹（真正的捏捏乐部分）。** 落地冲击转成一个**欠阻尼弹簧**的挤压量（`SQ_K 0.07 / SQ_C 0.19`，ω≈0.26 rad/帧、ζ≈0.37），渲染成屏幕坐标系的 squash & stretch，最多压扁 30%、回弹时反向拉长 13%。

⚠️ **单位必须是「每帧」，不是「每秒」**（这个求解器里 `G = 0.72` 就是 px/帧²）。第一版写 260/12 却按帧积分，ω·dt = 16 远超稳定上界 —— 弹簧离散后永远振下去，实测落地 9 秒后还在 ±11px 抖（61 次方向反转）。

⚠️ **挤压写在屏幕坐标系里。** 直接 `rotate(θ) scale(sx,sy)` 会沿**旋转后**的轴压扁，一颗躺着 90° 的水果就变成横向挤压。现在写的是 `R(−θ)·diag(sx,sy)·R(θ)` 展开成的 `matrix()`，只多四次乘法。

> ⚠️ **§二十一轮更正：这条已经改回「水果自己的坐标系」了。** 屏幕坐标系的挤压会把**已经旋转过的形状再转一次**（合成矩阵是 `diag(sx,sy)·R(θ)`，眼睛读到的角度变成 `atan2(sy·sinθ, sx·cosθ)`，最坏差 20°），访客看到的是「水果落地后奇怪的进行回正角度」。现在写的是 `rotate(θ) matrix(sx,0,0,sy,0,0)`，画上去的角度恒等于求解器的 `rot`（实测差 ≤0.005°）。见 §二十二。

⚠️ 挤压是**纯视觉**的：它从不碰 x/y/px/py，所以碰撞半径、堆叠行为和所有量测结论都不受影响。`--sq` 属性发布给探针（元素的 AABB 会跟着**旋转**变，量不出挤压）。

**实测（`fruit-bounce.mjs`，1440×950，从视口顶部落下）**：2174ms 触地 → 回弹 **97px**（约落差的 1/10）→ 4 次方向反转 → 挤压区间 −0.131…+0.300 → 最终**精确停在地面上（0.0px）**。

**堆叠没有回归**：`vpile.mjs` 5/5、`vpile-tail.mjs` 的四个窗口 604 → 97 → 24 → 21 → 20px/颗（衰减，不是嗡嗡响）。

⚠️ 顺手校准了 `vpile.mjs` 的阈值（25 → 60）：A/B 过 —— **把回弹关掉（`GROUND_BOUNCE = 0`）同一套流程也量到 26.5px/颗**，而开着回弹是 26–41px，所以那点残余不是回弹造成的，旧的 25 是单次好运的读数。这个断言的用处是抓**爆炸**（就是缺阈值时 134–187px 那种），收敛形状交给 `vpile-tail.mjs`。

### 三、催更计数接上 D1（这一节是复查别人写的那一版）

| | 旧 | 新 |
| --- | --- | --- |
| 接口不存在（`astro dev` 里必然） | **按钮完全没反应** | 照常跳、照常掉水果 |

## 十八、清掉 `astro check` 的 11 个错误（其中 3 个是真 bug）

访客把 VS Code / 终端的报错存在 `输入/报错/`（`问题报错.txt` 是 Problems 面板的 JSON，`终端报错.txt` 是 `npx astro check`）。**11 个 errors 全部清掉，现在是 0 errors / 0 warnings。**

⚠️ 这批错误之前一直挂着，被当成「别人的噪音」。实际上**三个是真 bug**：

| 报错 | 真相 |
| --- | --- |
| `fan.ts` ×2：`hero` 缺 `scroll` | **en 和 zh 都没写这个字段**，而类型和标记都要求它 —— hero 底部那行滚动提示在三个语言里**一直是空的**。补上 `↓ scroll` / `↓ 向下滚动` |
| `FanPage.astro`：`FanCopy` 上不存在 `langSwitchLabel` | 语言切换那一组的 `aria-label` 引用了一个不存在的字段 → 屏幕阅读器读不到这一组是什么。补 `Language` / `语言` |
| `FanPage.astro` ×2：`{ code: string }` 上不存在 `en` | `category: meta?.[ui] ?? meta?.en ?? image.folder` —— `meta` 是 `{ code }`，**两次查找永远是 undefined**，于是每张卡片的分类都退回文件夹名。英文页看不出来（`illustrations` 被 CSS 变成 ILLUSTRATIONS），但**中文页印的是「ILLUSTRATIONS」而不是「插画」**。改成读文案 `c.categories[image.folder]` |

⚠️ **第三行那条的教训**：一个**写错的类型注解**（`Record<string, { code: string }>`）把一次永远失败的查找变成了合法代码，错误就藏在「类型说没问题」后面。判据不是「构建通过」，是**中文页面上印出来的那三个词**。

### 剩下 8 个是工具链的坑，两个坑各修一次

**① `{/* … */}` 不能写在属性表里。** 两个文件各有一处把注释放在 `<img>` 的属性中间：

```astro
<img src={x} alt="" {/* ⚠️ 这里 */} loading={…} />
```

`astro check` 报的是 **"Unterminated string literal" + "':' expected"**，位置指向注释本身往下两行 —— 完全指不到真正的地方。`CassetteShelf.astro` 那处是**没有花括号的** `/* … */`，报出来的是另一条（`boolean` 不能赋给 `string`，附注说「所需类型来自属性 `is`」）。修法都是把注释挪到**子元素位置**（`{/* … */}` 在标签外），CassetteShelf 那边因此给 `<img>` 套了个 fragment。

**② `loading={index < n ? "eager" : "lazy"}` 这种属性里的 `<` 也不是元凶**（一度怀疑是它，把比较挪进 `coverLoading()` 函数后错误没消失 —— 真正的元凶是①）。函数版留着，因为它同时让属性表短了一行。

**③ 块级 `type` 与提升的函数声明。** `applyContactFriction(t: Sheep, …)` 写在 `if (sheepLayer) { type Sheep = … }` 的**外面**，于是 `Sheep` 看不见（`Cannot find name 'Sheep'`）；而 `spawn()` 是提升的函数声明，TS 在它内部**丢掉** `if (sheepLayer)` 的收窄（`'sheepLayer' is possibly 'null'`）。修法：类型提到外面，块内绑一个非空 const（`const layer: HTMLElement = sheepLayer`）。⚠️ 这两条和 `FanMosaic.astro` 里 `gl` 那次是**同一个 TS 行为**。

### 二、云朵破口入场（`src/components/FanIntro.astro`）

需求：「从 art 界面跳转到 fans page 时，以及第一次进入 fans page 时换一个加载动画……粉色画面，从底部升起云逐渐覆盖，最后云的中间破开一个口往四周扩展，展现主内容」。第一版是 CSS 关键帧 + 十几片云块，访客判定「有问题」，并给了一份独立演示（`云上旅梦 · Opening Animation`）。**现在这一版是那份演示的移植**，技术、时钟、揭幕编排全部照搬：

| 时间 | 画面 |
| --- | --- |
| 0.12 s | 约 200 个 puff 从画面下方升起（每个 0.95-1.4 s，错峰） |
| 1.90 s | 中间开始破口（1.60 s，ease-in-out） |
| 2.35 s | 页面 hero 开始入场：opacity 0 → 1 加 28px 上浮，每条 0.95 s，延迟 0/0.09/0.19/0.29/0.39/0.49 s |
| 3.50 s | canvas 撤下，覆盖层移除 |

- **云是"低分辨率离屏画布 + 每帧一次模糊"**：puff 画在按面积固定的缓冲上（`SCALE = clamp(sqrt(850000 / (W·H)), .34, .66)`），再用 `ctx.filter = blur(blurPx)` 合成回主画布——一次模糊，而不是每个 puff 一次。Safari < 16.4 没有 `ctx.filter`，回退到径向渐变软边。
- **破口是 `globalCompositeOperation = "destination-out"`**：主洞是一个径向渐变圆（中心全擦、边缘柔和），外面再擦 16 片会缓慢旋转的「花瓣」，所以边沿是撕裂感而不是一个圆。
- ⚠️ **画布就是封面，粉色底也画在画布上。** 演示里粉色底是 DOM 层，因为它盖住的就是演示自己的粉色页面；这里覆盖层盖的是真页面，DOM 里任何留在画布下面的东西，破口打开后都会继续挡着页面。所以底色（一条线性渐变 + 三个椭圆径向 + 被遮罩的白点纹理）一次性画进 canvas，破口一刀全擦掉。
  - ⚠️ canvas 的径向渐变**只有圆**，演示里是椭圆：每个椭圆用 `translate + scale` 包起来画（`ellipse()` 里那四行）。
  - ⚠️ 点阵必须先画在**独立画布**上再贴过来：直接对底色用 `destination-in` 打遮罩，会把遮罩以外的底色一起擦掉。
  - ⚠️ **覆盖层自己不能有背景**：第一版留了 `background: #ffd3e8` 当首帧兜底，破口打开后中间就是一堵粉色的墙——正是这段注释警告过的事，自己又犯了一次。兜底改成「循环启动前先同步画一帧」（`render(0)`），画布从第一帧就是不透明的。
- ⚠️ **揭幕对象是页面自己的 hero，不是复制一份标题卡。** 演示的 `.content > *` 就是它的页面。把那份文案复制进覆盖层，会在整个后半段让两个几乎重合的 wordmark 同屏；改成：`html.is-fi` 期间 hero 的子元素停在 `opacity: 0 / translateY(28px) / scale(.96)`，2.35s 时加 `html.is-fi-revealed` 用演示自己的错峰放出来。同一套编排，零重复 DOM。
- ⚠️ **演示的按钮和 chips 没有搬过来**：那是落地页的 CTA（「开始探索」「了解更多」「治愈系 · 插画集 · 云朵旅」），而这个 hero 按访客自己的要求没有 CTA，印章和「↓ scroll」正好占着那两个位置。
- ⚠️ **脚本是 `is:inline` 且不含 TypeScript 语法。** 它做的第一件事是把 `is-fi` 加到 `<html>` 上（那是压住 hero 的开关），而 Astro 的 module script 是 defer 的，也就是在文档解析完之后才跑——足够让 hero 先被完整画出来再被摁掉。inline 才会在这一行就执行，那时下面的 hero 标记还不存在。
- ⚠️ **`FanMosaic` 在覆盖层之后才渲染，句柄晚一步才存在**：一开始直接 `window.__fanMosaic.pause()` 是静默空操作（实测整个入场期间背景照跑）。改成循环里每帧试着拿句柄，拿到就暂停，结束时恢复。
- ⚠️ **`frame()` 开头必须有 `if (finished) return;`**：`__fanIntro.step()` 取消 rAF 时可能已经有一帧在飞，那一帧会用**实时时钟**盖掉冻结帧，并在超过 3.5s 之后把整个入场拆掉。
- 入口仍然只有两个：本会话第一次进 `/fan/`，或从任意 `/art` 页跳进来（`document.referrer`）；back/forward 不重播，`prefers-reduced-motion` 完全不播（CSS 直接 `display: none`，脚本连 `is-fi` 都不加）。另有 `<noscript>` 与 8s 兜底。
- **一处调试钩子**：`window.__fanIntro.step(t)` 停表并只画第 t 秒那一帧（演示自己也有 `__cloudIntro`）。这页截图要 0.3-1.7 s，比破口本身还长，这是唯一能拍到中间帧的办法——`输入/_scratch/fi-look.mjs` 用它出图。
### 三、性能（「画面有点卡」）

`输入/_scratch/fan-perf.mjs`、`输入/_scratch/fi-spike.mjs`，1440×950，真 GPU（去掉 `--disable-gpu`）：

| 窗口 | p50 | p95 | max |
| --- | --- | --- | --- |
| 静置，着色器在跑 | 4.2ms | 6.4ms | 10.8ms |
| 静置，着色器暂停 | 4.0ms | 5.9ms | 13.8ms |
| 画廊（跑马灯在动） | 4.2ms | 6.0ms | 11.5ms |
| 入场播放中（CSS 云块版） | 6.0ms | 10.7ms | 28.3ms |
| 入场播放中（现在的 canvas 版） | **2.8ms** | **4.3ms** | 14.8ms |

- ⚠️ **0.3-0.8s 的长帧不是入场造成的。** `fi-spike.mjs` 加了对照组（把会话标记写好，不播入场），同样的长帧照样出现；它们属于页面启动（着色器编译 + 上百张封面解码）。所以这一轮的结论是：**入场自己不产生长帧**，别再为那几个尖峰改动画。
- 结论：**canvas 版比 CSS 云块版更便宜**（p50 4.2 → 2.8ms，p95 9.7 → 4.3ms，峰值 28.3 → 14.8ms）：模糊只在低分辨率缓冲上做一次，云是画出来的，不是一个一个 DOM 层。
- 改的三处（都不动观感）：① 入场期间暂停 WebGL 背景（拿到句柄后立刻暂停，见上一节的 ⚠️），覆盖层是不透明的，着色器在最贵的时候做的是没人看得见的工作；② 跑马灯在 `html.is-fi`（入场中）和 `document.hidden`（后台标签）时**不写** `style.transform`，位置也不推进，恢复时不会跳；③ 画廊 `<img>` 加 `decoding="async"`（两三个副本 ≈ 上百个元素，同步解码会占主线程）。

## 二十一、画廊封面在入场里加载、循环周期重新量、字标居中（2026-09-30）

访客三条报告/需求：①「云朵加载动画完成后，翻到下面的画廊时，图片依旧要先加载出现，这个等待本应该在云朵加载动画时完成」；②「图片拖动到一定距离后，他会突然消失，从画面的另一边出现」——**之前没有，b688b63 也没有**；③ 字标出画（我烘焙 `TITLE_GAPS` 引入的）。

### 一、「图片突然消失、从另一边出现」的真因：卡片宽度 = 图片宽度

`.plate-media img { height: 100%; width: auto }` —— 一张画片有多宽，取决于它的图有没有解码：没解码时那是一个**空盒子**，解码后才长到真实宽度。于是两件事一起发生：

- **`lazy` 的那一份副本**（`coverLoading()` 让前两份 eager、第三份 lazy）要等被拖进视口才开始取图；图一到，**那张卡从空盒长到 160–430px，它后面每一张卡跟着平移**——眼睛看到的就是「图片突然消失，又从另一边冒出来」。冷加载实测：入场结束时只有 **45–47/67 张**就绪，剩下 20 张永远是滚到才取。
- **循环周期是脚本跑的那一瞬间量的，而那个量法本身也错了**：`scrollWidth / copies` 把轨道 `padding: 0 24px` 按份数算进去、又漏掉最后一个 gap，等于 `period + (2×24 − 16)/copies`。实测三排分别**长了 10.78 / 8.06 / 8 px**，每次取模回绕都整排偏那么多。

**修法两条：**

1. **入场期间把封面全部加载完。** `is-fi` 在时，脚本把每个 `.plate img` 的 `loading` 翻成 `eager` 并跑一遍 `warmPlates()`——不是只预热进缓存（那样真正的 `<img>` 仍要等滚到才取），而是**驱动元素本身**。冷缓存实测：**t=608ms 就 67/67 就绪**，而入场要跑到 3.5s，所以封面在访客能看见画廊之前就已解码、布局已定稿。没有入场时（会话内普通跳转）仍走原来的 `load` + 200ms。
2. **周期从卡片量，并在轨道尺寸变化时重量。** `measurePeriod()` 改成量 `cards[0]` 与 `cards[unique]` 的 `getBoundingClientRect().left` 差（亚像素，与 gap/padding 无关），并加 `ResizeObserver` 盯住 track —— 封面解码、媒体查询、窗口缩放，任何一种让轨道变宽都会重新量。

## 二十二、入场结束时那 7.5px 的横移，和水果的第二次「更弹」（2026-09-30）

### 一、「云朵动画播放完后，整体画面又稍微向右侧移动了一次」

**真因：入场的滚锁写在了根元素上。** `FanIntro.astro` 里原来是

```css
html.is-fi { overflow: hidden; }   /* 入场期间锁滚动 */
```

实测：只要**根元素**的 `overflow` 不是 `visible`，Chrome 就会给 **`body`** 预留一条 15px 的滚动条槽 —— 入场期间 `body.clientWidth` 是 **1425** 而不是 1440，于是所有居中块整体左移 7.5px（`.fan-hero` 122.5、云 580.8、字标 158.1、顶栏 122.5）。代码在入场结束摘掉 `is-fi`，画面**向右跳 7.5px** —— 访客看到的正是这一下。站点把滚动条藏了，所以屏幕上没有任何东西能解释它。

**修法：把 `body` 移出文档流 —— 和灯箱锁页面用的是同一个办法。**

```css
html.is-fi body { position: fixed; top: 0; left: 0; width: 100%; }
```

实测：`body.clientWidth` **1440→1440**，`.fan-hero` 全程 130（云 575、字标 134.7、顶栏 130 都不再变）；封面仍然 `0+1440`。锁本身没退化：入场期间 `window.scrollTo(0,600)`、合成 wheel 事件、以及**真实滚轮输入**（`Input.dispatchMouseEvent: mouseWheel`）三种都让 `scrollY` 停在 **0**；入场结束后 `scrollTo(0,700)` 正常滚到 700。⚠️ 入场只会在 **scrollY = 0** 时播放（会话第一次进 `/fan/`、从 `/art` 跳进来、切语言 —— 三者都是新文档），所以没有滚动位置需要保存，这个锁不需要记 `top`。

| `GROUND_BOUNCE` | 0.42 | **0.62** | 0.42 实测只有 0.27 的有效恢复系数（56px 的一跳，读起来是「闷响 + 抽一下」） |
| `GROUND_BOUNCE_MIN` | 4.5 | **5.5** | 恢复系数变高，静息penetration 也要跟着抬高，否则地面又开始永远抖 |
| `SQ_K` / `SQ_C` | 0.07 / 0.19 | **0.05 / 0.13** | ζ 0.37 → 0.29：过冲更远（−0.303 对 −0.141），回弹更慢，读起来是「捏捏乐」而不是「果冻」 |
| `SQ_GAIN` | 0.011 | **0.013** | 同样的落地压得更扁 |
| `SQ_MIN` | 1.6 | **1.2** | 轻一点的落地也给一点形变 |
| `SQ_MAX` | 0.30 | **0.42** | ⚠️ 改前**每一次真实落地第一帧就顶到这个上限**，也就是说「压多扁」其实是这个上限决定的，不是落地速度 |
| `CONTACT_REST` | 0.72 | **0.78** | 水果之间也带一点活力，否则弹起来的果子落进一堆「沙子」里 |

**复验（改后）**：`fruit-bounce.mjs` 五项全过（回弹峰值 **169px**、2 次方向反转、最终精确停在地面 0.0px、`--sq` −0.372…0.420）；`vpile.mjs` 五项全过；`vpile-tail.mjs` 每颗位移 **596 → 37 → 33 → 22.7 → 15.8 px** 单调衰减（「DECAYING：还在安定，不是嗡嗡响」），0 颗穿地、0 颗结束时还在形变。


### 三、水果「没有回弹、反而奇怪的进行回正角度」= 挤压写在了屏幕坐标系（2026-09-30 追加）

访客：「目前水果落地后并没有看到回弹，相反他们会奇怪的进行回正角度，而不是维持应有的随机角度」。

⚠️ **回弹一直在**（逐帧追踪：落地 32.7px/frame → 弹起 13.5px/frame → **回弹 123px**，用时 301ms）。看不到它，是因为**挤压把水果画歪了**：

旧写法把挤压放在**屏幕坐标**里 —— `rotate(θ)` 之后再乘 `R(−θ)·diag(sx,sy)·R(θ)`，注释里写的理由是「躺成 90° 的水果不会横向压扁」。代价是：**屏幕坐标的挤压会旋转一个已经旋转过的形状。** 合成后的矩阵是 `diag(sx,sy) · R(θ)`，眼睛读到的角度变成 `atan2(sy·sinθ, sx·cosθ)`：

| 画上去的角度 θ | 旧写法读起来是（sq=0.42） | 偏差 |
| --- | --- | --- |
| 20° | 10° | **−10°** |
| 45° | 25° | **−20°** |
| 70° | 52° | **−18°** |

也就是说：整个 ~300ms 的挤压—拉伸周期里，水果看起来都在往「水平/竖直」转 —— 正是「奇怪的进行回正角度」；而 123px 的竖直弹跳就藏在这个形变里，读起来只剩「抖了一下」。

**修法：把对角矩阵放回 `rotate` 里面** —— `rotate(θ) matrix(sx,0,0,sy,0,0)`，挤压沿水果**自己的轴**发生，画上去的角度就恒等于 `t.rot`。顺带少四次乘法加一对 cos/sin。

| 判据（`输入/_scratch/squash-angle-check.mjs`，新写的） | 旧写法 | 现在 |
| --- | --- | --- |
| 整个落地过程里 `\|眼读角度 − 求解器 rot\|` 最大值 | **20°** | **0.005°** |
| `\|算出来的 y − 求解器的 y\|` 最大值 | 0px | **0px** |
| 回弹高度 / 用时 | 123px / 301ms | **123px / 301ms** |

⚠️ 求解器的状态现在发布在 `window.__fanSheep`（和 `__fanRows`、`__fanIntro`、`__fanMosaic` 同一个约定）：**元素上只能读到合成后的 transform**，「求解器的 rot 是多少」「残余矩阵有多少」这类问题从 DOM 里答不出来 —— 这次就是靠它把「画歪了」和「真的转了」分开的。


### 四、按催更按钮掉下来的水果为什么不弹：**果子之间不会弹**（2026-09-30 追加）

访客：「手动拖动水果到空中后松开，下落碰到底部就会有弹跳。但是按那个催更按钮时，掉下来的水果没有弹跳动画」。

**先量再改。** 空地上掉一颗：回弹 **124px**；已经有 6 颗躺在地上时再掉一颗：第一次接触发生在**别的果子身上**（y=866，地面是 924），只**弹起 14px**、4 次方向反转 —— 是「抖一下」不是弹跳。原因很直接：**地板会反向法向速度，果子撞果子只会损失 22%**（`CONTACT_REST` 保留方向），所以整堆是一袋沙子；而催更按钮的果子恰好永远落在自己堆出来的那堆上 —— 访客一直盯着看的那个场景，就是唯一不弹的场景。

**改法**：`applyContactFriction` 里按撞击速度分档 —— 超过阈值（`CONTACT_BOUNCE_MIN = 14`，果子从视口顶掉下来约 35px/frame）就**反向**法向速度（`CONTACT_BOUNCE = 0.4`），低于阈值保持原来的耗散。和地板用的是同一套阈值思路（`GROUND_BOUNCE_MIN`）。

⚠️ **四个坑，全是量出来的**：

| 坑 | 现象（实测） | 修法 |
| --- | --- | --- |
| 一帧里被**两个**邻居先后反向 | 一颗果子沉进堆里同时碰到 2–3 颗，第二次接触看到的是「已经在远离」的速度，再反向一次 —— 直接按回堆里。堆上落地只剩 **14px** | `t.bounced`：**每个身体每帧只允许一次法向响应** |
| 一帧里对**每个**接触都做一次法向耗散 | `0.78³/帧`，两帧就把回弹吃光 | 第一个接触定调，其余只走 `CONTACT_REST_EXTRA = 0.92`（不是 1：完全不耗散时堆永远达不到睡眠阈值，`vpile-tail` 在 ~25px/颗 处平台化） |
| 同帧又碰地板又碰果子 | 两边各反向一次，互相抵消（124px 的地板回弹量成 **21px**） | 地板分支也置 `t.bounced = true` —— 它是这一帧的第一次法向响应 |
| 弹起来那一帧还在被 `CONTACT_DAMP` 耗散 | 回弹还没走出去就被咬掉 | `if (t.contact && !t.bounced)`：**弹起来后的那一帧不阻尼**（地板本来就不会阻尼，这样两边一致） |

**结果**：同样「已有 6 颗」的落点回弹 **14px → 76px**；堆的衰减（`vpile-tail.mjs`，连跑两次）仍然是 **DECAYING**，0 颗穿地、0 颗结束时还在形变。

⚠️ **`vpile.mjs` 那条 60px/颗 的断言是「单次抽样」，本身会抖**：同一份代码连跑两次，一次 PASS 一次 167.8px/颗（把回弹完全关掉的旧行为也一样，一次 PASS 一次 FAIL）。所以**判据用 `vpile-tail.mjs` 的衰减曲线**，那条断言只当「爆炸探测器」。同样地，这个无头环境里帧率会被压到 14–20fps，`Math.min(32, now-lastT)` 一夹，整个模拟进入慢动作，`fruit-bounce.mjs` 的回弹读数在 19–250px 之间飘 —— **同一份代码的 A/B 必须交替跑**，这次交替 A/B 的结论是：关掉这套改动 31/0px、开着 72/207px，即**这两个改动不会削弱地板弹跳**（一颗果子时根本没有接触，那些数字就是环境噪声）。

### 五、整页禁止选择文本（2026-09-30 追加）

访客：「给整个界面加一个防止复制，这样和水果互动的时候不会误点变成左键拖动选择文本」。

- `.fan-root { user-select: none }` —— 拖水果是左键按下开始的，页面里全是段落，浏览器同时也开始划选，玩具就被拖着一片蓝底走。

- ⚠️ **留了一个例外**：`.contact-handle`（没有公开链接的那种联系方式：Discord / QQ）仍然可以选中 —— 那是这一页唯一「存在的意义就是被复制」的文字。要连它也禁，删掉那两条 `:global(.fan-root .contact-handle)` 即可。

实测（CDP，三种语言）：`.fan-root` 的 `user-select` 全是 `none`，段落的可选中字符数 **0**，handle 可选中 **7** 个字符；`/about/` 等其它页面 `user-select: auto` **完全没被影响**。


### 六、真正的元凶：「第一次落地弹不弹」是个**抽奖** —— 撞击速度读在夹到地面之后（2026-09-30 收尾）

访客最后一条反馈是钥匙：「你在刚刚的修改中，有好几次达成了我要的第一次落地弹跳，但是你依旧改没了……目前状态是水果第一次下坠落地不弹」。**代码里没有任何一次改动是冲这个去的**，但它就是会时有时无 —— 因为它取决于**落地那一帧水果离地面还剩多少**。

⚠️ **`vn` 量错了地方。** 原来是：

```js
if (t.y > FLOOR) {
  t.y = FLOOR;                    // ← 先夹到地面
  const vn = t.y - t.py;          // ← 于是 vn 是这一帧「陷进去的深度」
```

所以 `vn` **不是落地的速度，而是这一帧从上一帧位置到地面剩下的距离**。定量的例子（`输入/_scratch/drop-test.mjs`，把水果放在固定高度、零初速再放开）：下落 29.05px/帧、地面还剩 10.65px → `vn = 10.65`，恢复系数作用在 **37%** 的撞击速度上 → 回弹只有 **6.6px/帧**（应该是 29 × 0.62 ≈ 18），整段弹跳只有 26px；而剩下的深度再小一点就掉到 `GROUND_BOUNCE_MIN` 以下 —— **那一帧完全不弹**。

- 它还跟**帧率**反着来：dt 越大（帧越慢），一帧跨过的距离越大、剩下的深度越小，弹跳就越弱甚至没有；
- 也正因为如此，同一份代码、同一次满高度下落，实测回弹在 **0 / 19 / 34 / 40 / 117 / 124 / 137 / 152 / 250px** 之间乱跳（§二十二 的表就是在这个误差里做的 A/B —— 数字本身是那个抽奖的读数）。

**修法一行**：先量、再夹。

```js
if (t.y > FLOOR) {
  const vn = t.y - t.py;          // 撞上之前这一帧真正走过的距离＝撞击速度
  t.y = FLOOR;
```

**修后实测（同一支定速探针）**：y=200 放开 → 撞击 **18.35px/帧**、回弹 **203px**（383ms）；满高度（y=−20）→ 撞击 20.69px/帧、回弹 **256px**；连跑两次数字一致，**不再是抽奖**。挤压也因此被正确驱动（内部峰值 1.04，渲染仍按 `SQ_MAX=0.42` 截断）。堆的衰减复验仍然是 **DECAYING**、0 颗穿地、0 颗结束时还在形变。

⚠️ **教训**：这一轮里我先后把 `GROUND_BOUNCE` 从 0.42 提到 0.62、调软弹簧、给果子之间加回弹 —— 全都在**修一个读数本身有 0–250px 随机误差的系统**，所以访客看到的是「有时候有、有时候没有」，而我看到的是「有时候 124px、有时候 19px」，两边都觉得对方在说另一件事。**先让测量可重复（定速、定高、零初速），再调参数。**


## 二十三、手机端一轮（2026-10）：字标间距、水印位置、行头贴边

访客：「针对手机网页端进行优化一下，主要看几个大界面，详细项目里面不需要管。粉丝页则是开头的标题
RRSUIKA STUDIO 这些单词之间间隔有点远（这是我们针对 2k 显示做的字距优化，但是手机上看就很奇怪）。」
「你可以用识图功能进行检查，避免一段标题被截断成两行，字间隙过大等问题」——所以下面每条都是**先量后改、改完再拍图看**。

### 一、`TITLE_GAPS` 是 px，字标却会缩 —— 手机上是 `RRSU IKA STUD IO`

真因不是数字错，是**单位错**。那 14 个数字是在 2K 窗口里、`.fan-title` 顶到 `clamp()` 上限 **108px** 时逐对调出来的，
但一直在标记里写成字面量 `px`。字号缩、间距不缩：

| 视口 | 字号 | `U` 后面的间距 | 占一个字符advance的比例 |
| --- | --- | --- | --- |
| 2K（调参时） | 108px | 19.5px | 18% |
| 手机 390 | 29.64px | 19.5px | **66%** |

14 个字里光是人工间距就吃掉 **63.25px**，字标总宽 367px —— 手机上一行只剩 390px，看上去就是四个词。

**修法：`TITLE_GAPS` 的数值一个都不动，只把它除以调参字号再写成 `em`。**

```js
const TITLE_GAP_BASE = 108;                       // .fan-title 的 clamp 上限＝调参字号
const titleGap = (px) => `${(px / TITLE_GAP_BASE).toFixed(4)}em`;
```

标记里 `margin-right:${titleGap(TITLE_GAPS[i])}`。`em` 在这里是**这个 span 自己**的字号，而 `.tl` 不设字号、继承 `.fan-title` —— 正是要的那个（`docs/pitfalls.md §4` 说的是反例：`em` 落在谁头上要先问清楚）。

实测：390 手机上字标 **367px → 321px**，`U` 的间距按 0.1806em 缩到 5.35px；2K 上（字号已经顶到 108px）**逐像素不变**。
副作用是好的：1440 以下的桌面宽度本来也有同一个毛病（108px 是上限，不是常数），现在一起正了。

### 二、水印 `.fan-hero-echo` 挂在 hero 上，字标却跟着云走

水印是**绝对定位在 `.fan-hero` 上**的（`top: clamp(214px, 17vw, 236px)`），字标是**在流里**排在云下面的。
窄屏那条 `@media (max-width: 560px)` 给 `.fan-title` 加了 `margin-top: clamp(196px, 50vw, 212px)` 把字标往下推，**水印的那条 `clamp` 没有跟着推**。

实测 390：水印盒子 247..308，字标 365..398 —— 中间空 **57px**，画面上是一行孤零零的 `Fluffy World` 浮在字标上方，读起来像第二个标题而不是水印。
（768 以上是好的：水印 269..347、字标 315..379，压在一起。）

**修法：两条规则读同一个变量，并且把「云会缩小」这件事一起算进去。**

```css
@media (max-width: 560px) {
  .fan-hero { --fan-title-lift: clamp(196px, 50vw, 212px); }
  .fan-title { margin-top: var(--fan-title-lift); }
  .fan-hero-echo { top: calc(var(--fan-title-lift) + min(216px, 60vw) - 116px); }
}
```

`- 116px` 的来历：字标的流起点 = `云高 − 80`（`.hero-blob` 的负下边距）`+ lift`，水印要落在它**上方 0.59 × 自身盒高**处 —— 0.59 就是桌面那组的比例（768：水印 269、字标 315、水印盒高 78，46/78 ≈ 0.59）。
⚠️ **第一版写的是固定 `+ 133px`，在 360 上刚好、在 320 上就飘了**：`.hero-blob` 是 `min(216px, 60vw)`，320 视口下云矮 24px，而固定偏移不会跟着矮。所以这一项必须是 `min(216px, 60vw)`，不能是常数。

实测：320 / 360 / 560 三个宽度，水印盒顶都在字标顶**上方 36px**，三处一致。

### 三、画廊的行头（`01 ILLUSTRATIONS … 9 WORKS`）贴着屏幕两条边

`.fan-bleed` 是 `padding: 38px 0`（横幅是要出血的，画片本来就该顶到边），而 `.row-head` 在这个出血容器里 —— 它自己没有横向内边距。
实测 390：`.row-idx` 是 **0..15.2**、`.row-count` 是 **336.8..390**，两个数字分别贴在左右玻璃上。
字其实没被裁掉，但**贴着屏幕边的字看起来就是被裁掉的**，而且上面那块 `.bleed-head` 是有 18px 内边距的，同一页两套规矩。

**修法**：`@media (max-width: 560px)` 里给 `.row-head` 补上 `.bleed-head` 同款的 `padding: 0 18px`。

### 五、画廊的每一张画都被同一副画框切过（2026-10，同一次反馈的后半段）

访客：「fan page 的画廊的图片有问题，所有图片外框尺寸一样，导致有的被切断一半，有的右侧空一半的空间。」

**真因一行 CSS**：`@media (max-width: 640px)` 里的 `.plate { width: 168px }`。
桌面从来没有这个问题，因为桌面**没有**固定宽度 —— `.plate` 是 `flex: 0 0 auto`，宽度由自己的封面决定（`.plate-media img { height: 100%; width: auto }`，按比例缩放）。手机那条把画框钉死了，于是画框不再跟着画走。

这一页是**故意混规格**的，先量（`sharp` 读原始文件，排除 `cover.png`）：

| 行 | 张数 | 比例 |
| --- | --- | --- |
| illustrations | 9 | **0.602 – 1.778**（02-palasi 1669×2773 对 01-xiaoke 1920×1080，跨度 **2.95×**） |
| fashion-design | 4 | 全部 0.667 |
| food-art | 6 | 全部 1.000 |

390 手机上按旧规则的实测：

| 画 | 比例 | 旧行为 |
| --- | --- | --- |
| 01-xiaoke | 1.778 | 245px 的画塞进 152px 的内框 —— **切掉 93px**（「被切断一半」） |
| 02-palasi | 0.602 | 只画出 83px，168px 的卡片右侧**空着**（「右侧空一半」） |

**修法：手机端删掉那行 `width`，并给 media 一个「地板高度」。**

```css
@media (max-width: 640px) {
  .plate { height: auto; }        /* 内容高，两行标题不会被数字裁掉 */
  .plate-media { height: 176px; }
  .row-view { height: 258px; }
}
```

⚠️ **那个 176px 不是随便挑的，它有下限。** 宽度不再钉死之后，卡片宽 = `max(封面, 说明文字)`；封面比说明还窄的话，右侧那条空白就又回来了。这一档最长的说明是「UNCONSCIOUS MONSTER MOUSSE」（11px + 0.6px 字距 ≈ 135px），而最窄的竖构图是 0.602 —— 于是 media 至少要 `135 / 0.602 ≈ 146px`。176px 让每一行都稳稳高过它。

⚠️ **`@media (max-width: 560px)` 里那一组 `206 / 148` 一并删掉**：它压在 640 那组 `196 / 138` 上面，意思是**屏幕越窄卡片越大**，而且两个值都在上面那条下限之下，所以每一张竖构图都会留缝。现在只有一组数字、只写在一个地方。

### 六、那剩下的 2px：`.plate-media` 被挤扁了

改完之后 640–820 这一档还有 **1.2–3.6px** 的缝。真因不是宽度，是**高度**：`.plate` 是列方向的 flex 容器且带固定高度，子项默认可以收缩 —— 而 media 是唯一收得动的那个。

实测 768：`.plate { height: 238px }` 比它自己的内容**矮 2px**，于是 media 被压 `178 → 176`，`height: 100%` 的封面跟着缩小 → 框 316×176 对 312.9px 的画（crop −3.6px，正好是 `2 × 1.778`）。

**修法两条**：`.plate-media { flex-shrink: 0 }`（画永远不做吸收坏高度的那个），以及 820 档的 `.plate { height: auto }`（238 → 内容高 238，实测不变，但两行标题不会再挤）。

### 七、验证方式：逐张比「画的宽」和「框的宽」

`输入/_scratch/fan-plate-check.mjs`（本轮新增）在三行上逐张断言：

| 判据 | 含义 |
| --- | --- |
| `crop = imgW − boxW > 1` | 画比框宽 → 被裁 |
| `gap = boxW − imgW > 1` | 画比框窄 → 留空 |
| `distort = \|画的比例 / 文件比例 − 1\| > 1%` | 被拉伸 |
| `period == 一行真实宽度` | 循环接缝没有漂 |

**320 / 360 / 390 / 430 / 600 / 768 / 820 / 1024 / 1440 九个宽度全绿**（19 张画 × 每个宽度：crop 0、gap 0、distort ≤0.0001）。

⚠️ **变量宽度的车牌不会破坏循环**：`measurePeriod()` 读的是**排好版的两张卡之间**的距离（不是常数），track 上的 `ResizeObserver` 在封面改变布局时重测 —— 这正是桌面一直在走的代码路径。探针里那条 `period` 断言是这一点的证据。

⚠️ 写探针时的两个自伤（都已修正，记下来）：`period` 的期望值少算了一个 `gap`（`card[0] → card[n]` 跨 **n** 个 gap 而不是 n−1），以及**在模板字符串里给变量名加反引号** —— `docs/pitfalls.md §12.2` 记过同一条，这次是注释里的反引号把探针自己的模板字面量截断了。

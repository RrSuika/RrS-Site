# 条目写作指南：Project / Lab 文章（en / zh / nl）

> **什么时候读**：写新条目、改写旧条目、或审校任何 Project / Lab 正文之前。**必读。**
> **和谁配合**：`docs/writing-style.md`（规则 14–23，硬规则）、`lieflat-less-ai-tone` skill（成稿清理）、
> `dot-skill` 的 persona_analyzer §1「表达风格」（文风分析）。
> 三者冲突时：**writing-style.md 的硬规则 > 本文 > skill 的通用规则**。写作风格文档永远优先于
> 「去 AI 味」的通用规则，因为它描述的是这位作者的真实写法。
>
> 本文是把三个参考网站的拆解、本站语料实测数据、以及历次改写积累的经验合并成的一份规范。

---

## 0. 三条不可违背的前提

1. **不许新增事实。** 器件型号、数值、日期、因果、动机、个人经历，原文没有就是没有。拿不准先问用户。
2. **不许改渲染层。** 不改 CSS / 组件 / 布局 / 脚本。只改 `src/content/entries/*/*.md`。见 §9。
3. **技术可信度优先于文笔。** 一句话读起来再顺，只要工程上不成立就必须改。见 §6。

## 1. 参考网站拆解

三个参考站：**spritesmods.com**（Sprite_tm）、**bunniestudios.com**（bunnie）、**yopiemaker.com**（Yopie）。
拆解样本：VapourDeck、E-ink digit clock、On reading SRAMs in IR images、Baochip-1x、
Use the Force (Feedback) to Solder Small Things、Arduino SPWM generator、Functional Test EGS002、
Zero Crossing Detector。

### 1.1 叙事与结构

| 手法 | 具体做法 | 例证 |
|---|---|---|
| **用情境开场，不用定义开场** | 第一段是「什么事促使我做这个」，不是「本项目是一个……」 | Sprite_tm 的时钟篇开头是「我和我太太都不戴表」；VapourDeck 开头是小时候那台二手 PC-XT 和叔叔送的 486 零件 |
| **需求写在情境之后** | 读者先在乎，再看规格清单 | 时钟篇：「我列了一张这张钟必须做到的清单」：电池供电、白天和暗光下都能读、够大、免维护、**而且要有意思** |
| **需求里可以有非工程项** | 「有意思」本身就是需求 | 「如果我要做东西，至少得让人看一眼发出『哦？』」 |
| **分段用「发生了什么」命名，不用模板名** | Intro / Design / Hardware / Firmware / Final result | 而不是「项目背景 / 需求分析 / 实现过程 / 总结」 |
| **结尾报结果 + 交东西** | 不写总结段 | 时钟篇结尾讲了个真事：客人以为那几个数字是贴纸，直到翻页才发现是钟；然后给出开源文件和「做出来了记得告诉我」 |

### 1.2 技术文档手法

- **型号和数值是证据，不是装饰。** BP-6MT、TP4057、HT7833、ESP32-C6-WROOM-1、GDEY037T03、240×416、24-pin FFC；直接写，不翻译成通俗说法。
- **数字用来讲约束的故事**：「RLE 把需要的存储从 120K 压到 11K 多一点，给代码留了 4K 左右」。
- **失败按「后果链」写，并标注自己的意外**：
  > 「我没预料到的是它还有第二个效应：失谐的天线让射频放大器在校准时耗电大增……这超过了 500mA 的 LDO，导致欠压，芯片复位。」
  作者甚至在前面埋了伏笔：「正常情况下（伏笔……）足够带动主芯片」。
- **妥协就说是妥协**：「这不是最好的办法，但考虑到 WiFi 在这个项目里用得很少，我认为可以接受。」
- **测量与推断分开写**：bunnie「实际的存储单元小到看不见，但我们可以推断它的尺寸必须是……」
- **未解决的问题明写出来**：「值得问一句，攻击者能不能『就用很隐蔽的方式做几个字节的 RAM』」。
- **负面结果就是结果**（Yopie 的过零检测篇最典型）：示波器测出来中断发生在 Vcc/2 而不是过零点，所以占空比不是 50%，而且检测结果受输入幅度影响；然后他明确说哪种用法不受影响（测频率不受影响）。
- **可复现的程序**（EGS002 篇）：期望电压 2.55V / 3.15V / 0.55V / 3.4V / 4.4V，以及每个故障对应的 LED 闪几下。
- **对媒介本身的不确定也说出来**：「下面的图试图说明它，但你可能直接看代码更好」。

### 1.3 语感

- 全程第一人称，**包括承认不懂**：「我当时对硬件的具体知识其实不多」。
- **反营销**：没有任何东西被称作革命性；最强的断言也带机制：「我估计一年多一点才需要给这个钟充电」。
- 幽默是干的、括号里的，且不替代信息：「本网站完全符合 Web1.107rc1 标准」。
- 段落长度跟着内容走：一行成段用来下判断，长段用来推因果链。

### 1.4 三站差异（按需取用）

| | 特征 | 适合借鉴什么 |
|---|---|---|
| **Sprite_tm** | 编年体手工日志，带需求清单，多页分阶段 | 本站 Project / Lab 的**主骨架**：情境 → 需求 → 阶段 → 结果 |
| **bunnie** | 论点驱动的技术随笔，先立论，再逐条抵御他点名的替代方案（CHERI / PMP / MPU） | 借鉴「**把你否掉的方案点名说出来**」这个习惯 |
| **Yopie** | 手册体：编号步骤、期望仪表读数、可下载的原理图和代码 | 借鉴「**测量纪律**」：数值 + 条件 + 判据 |

> ⚠️ 三站只是**编辑参考**，绝不是关于本站项目的事实来源。不许抄句子、不许照搬段落、不许移植他们的轶事。

| 正式程度 | **3 / 5** | 技术随笔，非学术非营销 |

**高频内容词**（去停用词后）：test, control, motor, page, temperature, material, strip, current, power,
enclosure, design, resistance, encoder, wiring, heat, colour, white, rail, oled, filament, module, load。

→ 全部是**实物与量**（器件、材料、通道数、温度、电流、电阻），**没有一个是抽象评价词**。

机器标识符（GPIO21、A4988、TCA9548A、SH1106、FCOB、EC11）直接写在句子里，**从不翻译成通俗说法**。

## 3. 文章结构

### 3.1 Project（A–E）

同一个叙事逻辑，**标题说明实际内容，绝不出现 Introduction / Process / Conclusion 这种模板名**。

| 槽位 | 功能 | 首选标题 | 允许的变体（仅当首选词不真实时） |
|---|---|---|---|
| **A** | 这是什么、为什么存在 | `Background` | `The Assignment`（确实来自外部委托的项目） |
| **B** | 需求、任务书、约束、指标 | `Requirements` | `Design brief`（确实存在书面任务书时） |
| **C** | 工作本身：调研 → 概念 → 选材选件 → 制作 → 迭代 → 调试 | **按实际发生的事命名**（`Research and ideation`、`Solution`、`Building it`、`Design Iterations`、`Technical Verification`） | 无 |
| **D** | 已核实的结果 | `Result` | `Current Status`（仅 WIP 项目） |
| **E** | 这件事确立了什么 / 还剩下什么 | `What I Learned` | `What's Next`（当这一节确实是前瞻而非回顾） |

**规则**
- A **不得复述标题**。用 1–3 个短段说清触发事件或问题。
- B **只在原文确有关系清单时存在**。绝不为了填模板造一张需求表。
- C 是正文，可以多个 H1。按**工作阶段**切分，不按文档类型切分。
- D 必须区分**设计 / 已装配 / 已演示 / 已实测验证**。做出原型 ≠ 已验证。
- E 必须针对这个项目。不要通用收尾，不要复述 D。
- 短项目用紧凑式：A → C → D → E，或 A → B → D。**不够就短，绝不注水。**

### 3.2 Lab（A–E）

| 槽位 | 功能 | 首选标题 | 允许的变体 |
|---|---|---|---|
| **A** | 要查证的问题 | `Objective` | `What I Built`（构建型条目）、`Background`（以情境开场的条目） |
| **B** | 设备、元件、条件、方法 | `Setup` | `Test Setup` / `Hardware` / `Wiring` |
| **C** | 实际发生了什么、测到了什么 | **按实际命名**（`The Bugs`、`Experimental Log`、`Test 1–15`） | 无 |
| **D** | 能得出什么结论、不能得出什么 | `What This Shows` | `Limitations`、`Cautions`（原文就是警告口吻时） |
| **E** | 下一个实验或改动 | `What's Next` | **原文没有下一步就省略，不许编** |

**Lab 专属规则**
- **测量值 / 个人观察 / 理论预期 / 未验证假设，四者必须可区分。** 绝不把「我认为原因是……」升级成「原因是……」。
- **失败的实验就保持失败**，不确定就保持不确定。绝不事后包装成成功。
- Lab 条目保持**窄**：一个问题。已经长成构建日志的 Lab 条目，**不要假装把它收窄**，但保持
  Objective → Setup → 观察 → 局限 的形状。
- Lab 与 Project 的关系用正文一句话表达，**不引入新的链接语法**。

### 3.3 语言内的标题写法

| | 首选 | 变体 |
|---|---|---|
| EN | `Background` / `Requirements` / `Result` / `What I Learned` | `The Assignment` / `Design brief` / `Current Status` / `What's Next` |
| ZH | `背景` / `需求` / `结果` / `学到的东西` | `项目背景`（委托类）/ `设计任务书` / `当前状态` / `下一步` |
| NL | `Achtergrond` / `Eisen` / `Resultaat` / `Wat ik heb geleerd` | `De opdracht` / `Ontwerpopdracht` / `Huidige status` / `Volgende stap` |

Lab 槽位 A：EN `Objective` / `What I Built` / `Background`；ZH `目的` / `做了什么` / `背景`；
NL `Doel` / `Wat ik heb gebouwd` / `Achtergrond`。

## 4. 列表 ⇄ 散文

本站列表密度 **20.7 项 / 千词**，参考站接近零。要**有选择地**改，不是一刀切。

**改回散文**：条目本身就是被切碎的论证句（每一项都是完整分句、顺序承载推理、没有一项是数据）。

**保留列表**：本身就是数据或流程
- 引脚表 / 接线表及其 bullet 形式
- BOM、材料对比表、颜色通道表
- 编号测试流程与测试记录（`Test 1 … Test 15`）
- 读者要按顺序执行的步骤
- 场景 / 预设枚举

**合并时不许删项**，每一项事实都要留下。

## 5. 去 AI 味：可执行触发标记

按 `lieflat-less-ai-tone` 的白名单执行：**只改命中规则的部分，其余逐字保留，不改文章框架。**
本站已做过的清扫记录：

| 规则 | 触发标记 | 改法 |
|---|---|---|
| 1 翻案腔 | 「不是……而是」「并非……而是」「不在于……而在于」「不只是……还有」「看似……实则」；EN `not X, but Y` / `not just X, but Y`；NL `niet X, maar Y` / `Geen X, maar Y` / `niet alleen…maar ook` | 直接正面下判断，先给判断再给依据。**中文这条是零容忍（规则 21①）** |
| 2 顿号密集 | 一个分句内两个以上顿号连接三项以上并列 | 能概括就概括；必须保留三项以上时打散其中一项的句法 |
| 3 相邻句同构 | 连续两句以上逗号数相同、成分顺序相同、长度接近 | 打散其中一句的句法 |
| 4 破折号 | 揭晓式破折号 | 写完整句子，或改逗号句号 |
| 5 冒号滥用 | 提示语（「一句话总结」「核心是」「关键在于」）引出内容；空转句引出列表 | 删提示语直接写内容；或把提示语写成有内容的判断 |
| 6 序数小标题 | 小标题用「一、二、三」通篇编号 | 删编号保留文字。**正文里的「首先……其次」不改** |
| 7 拟人化喻体 | 「像一位智慧的导师」「永不疲倦的审查员」 | 换成这东西实际做了什么 |
| 8 具体数据被概括词盖掉 | 同段已有具体值，却写「显著提升」「大幅增长」 | 把已有的具体值提到概括词位置。**原文没有数据就不许编号** |
| 9 禁用起手式 | 「说白了」「说穿了」「先说结论」 | 删掉直接给判断 |
| 10 翻译腔（只五种） | 过长前置定语（>15 字修饰）；「当……时」前置从句；前置话题壳「对于……来说」；句首连接词「然而/因此/此外」；「这意味着/这表明」复述句 | 各按对应改法；**未列出的表达不能以「翻译腔」为由修改** |
| 11 段首零主语评论 | 非首段以「听起来/值得注意的是/关键在于」开头且整句无回指成分 | 补一个「这」或点明评论对象 |

**不作为改写理由**（硬约束，别改）：句长/段长不够参差、虚词偏少、被动句、名词化、长句本身、
正文里的「首先其次」、句内同构排比、问句/设问、比喻本身、抽象名词配具体动词。

**EN 专属**：模板短语（Furthermore / Moreover / It's important to note / plays a significant role）
不得出现；过度修饰词（delve / leverage / utilize / crucial / robust / seamless / cutting-edge /
revolutionary）在修辞语境禁用。
**NL 专属**：句首 echter / bovendien / daarnaast 避免；voorts / derhalve 这类古旧词避免；
「het is belangrijk om te benadrukken」类模板句不得出现。
**保留项（三语通用）**：事实性否定（「我没做弹道测试」）、规格注记、代码注释、口语化片语。

## 6. 技术可信度审查（新增维度，必做）

**AI 润色过一轮的文本必须当作不可信来源重新核查。** 实测中已经查出过：把逆变器接在 MPPT 的
LOAD 口上、Class T 熔断器分断能力写错 10 倍、用直流布线指南评判 230V 交流回路。这类错误读起来
毫无破绽，只有重算才会暴露。

### 6.1 必做动作

1. **所有算式重算一遍。** 欧姆定律、压降、I²R、效率连乘、容量换算；逐个用计算器验。
   写进文章的数字必须能自洽。
2. **所有额定值对照器件实际能力。** 端子载流、线径载流、保险丝分断能力、电容耐压、GPIO 电流。
3. **拓扑要能走通。** 电流从哪来、经过谁、回到哪。任何一个环节的载流能力对不上，整个拓扑就是错的。
4. **区分 AC 与 DC 规格。** 熔断器、断路器、继电器、开关的分断能力几乎都有 AC/DC 两套数字，
   **混用是常见错误**。
5. **区分标准体系。** 直流系统的布线指导（如 Victron Wiring Unlimited）不能拿来评判 230V 交流回路；
   交流要看 NEN 1010 / IEC 60364。
6. **医疗 / 安全类断言要有标准出处。** 「比触电导致室颤更快」这种话，要么给出标准条款
   （如 IEC 61008：额定剩余电流下 300ms、5 倍额定值下 40ms），要么删掉。

### 6.2 高频 AI 编造模式（重点怀疑对象）

| 模式 | 例子 | 怎么识破 |
|---|---|---|
| **虚构的器件能力** | 「6 端口 MPPT，母线内置」 | 查这个器件真实存在吗？端子真的能载这个电流吗？ |
| **拓扑上不可能的连接** | 100A 逆变器挂在 MPPT 的 LOAD 口 | 顺着电流路径走一遍，看每个环节的额定 |
| **单位/量级错误** | Class T 200kA（实为 20kA DC） | 查厂商 datasheet 的分断能力，注意 AC/DC |
| **把直流经验套到交流** | 用 2.5% 直流压降指导 230V 回路 | 判断这条经验出自哪个标准体系 |
| **圆整得可疑的数字** | 电阻、效率、温度全是整数 | 自己按公式算一遍，看能不能复现 |
| **无出处的因果** | 「因为 X 所以 Y」，但原文没有验证过程 | 原文有没有记录这个因果是怎么得出的？没有就降级为「我认为」或删掉 |
| **夸大的机理** | 「铜箔胶带扛不住 2A」 | 按截面积算载流；真实的失效模式往往是**接触电阻/胶层**而不是铜本身 |

### 6.3 发现可疑内容怎么处理

- **能靠算数确定的** → 直接修正，并在报告里说明改了什么。
- **需要知道实际硬件才能判断的** → **停下来问用户**，不许猜。典型：这块板子到底是什么型号、
  这个端子实际能过多大电流。
- **仅仅是措辞不严谨的** → 改成工程上站得住的表述（例如把「扛不住 2A」改成「接头靠胶不靠金属，
  热量积在接头处」）。
- **绝不把未核实的结论写进文章。** 也绝不把「待核实」这类编辑批注留在正文里，除非用户明确授权。

## 7. 术语、单位与格式

- **器件与型号标识符不翻译**：ESP32、A4988、TCA9548A、SH1106、EC11、FCOB、INMP441、NEMA17。
  封装尺寸按行业叫法（42mm 步进电机 = NEMA17）。
- **数值与单位格式不动**：`3×80A`、`92–95%`、`24V`、`240×416`、`47µF / 50V`。
- **EN 用美式拼写**（用户 2026 指示）：color / behavior / modeling / organize / optimize / fiber /
  molding / center / initialize / analyzed / defense / liters。
- **NL 保留行业惯用的英文技术词**：prototype、workflow、embedded、feedback、interface、hardware、
  software、controller、sensor、module（规则 14）。
- **ZH 用通用中文工程术语**，标识符保持拉丁字母（规则 16）。可自然夹英文术语，不强行翻译也不刻意插。
- **破折号一律禁用（用户 2026 指示，全站含 art 条目）。** `—`（em dash）、`――`、`——` 一个都不留。
  替代按优先级：**分号 `;` / `；`** → **括号 `()` / `（）`** → 逗号 → 冒号（仅当确实是引出说明时）。
  英文用 `;` 或 `(...)`；中文用 `；` 或 `（...）`；荷兰文用 `;` 或 `(...)`。
  例：`Fashion Design — Ibuki Suika Series` → `Fashion Design (Ibuki Suika Series)`；
  `Ibuki Suika — Design #1` → `Ibuki Suika; Design #1`；`小刻 — Sept 2026` → `小刻 (Sept 2026)`；
  表格里表示「无」的 `—` 改为文字（EN `None` / ZH `无` / NL `Geen`）。
  **数字区间的 en-dash `–` 保留**（`92–95%`、`Test 1–15`），它和破折号不是一回事。
- **headings 里的冒号用全角 `：`，不是 `；`。** 见 §10。
- **`tags` 字段冻结**：必须与列表页 `filterTags` 逐字一致，**永不改动**。`translationKey` / `lang` /
  `type` / `cover` / `date` 同样不动。`title` / `description` / `gallery[].title` 可以润色。
- **`spineTitle` 是印在磁带脊上的图形标签，语言中立**，三语文件用同一个字符串，**不要翻译**。

## 8. 三语本地化方法

**英文是唯一规范源。**

1. 先把英文改好，对照证据复核一遍。
2. 抽出**断言集**：事实、数值、限定、不确定、结论。
3. zh 和 nl **从断言集独立写**，不是逐句照英文翻译。
4. 反向比对：zh/nl 的每条断言都要能追到英文（或反过来：原文 zh/nl 若比英文多出细节则以它为准）。
5. **标题结构一致**（同槽位、同顺序、同 H1 层级），但**标题措辞按各自语言自然写**。
6. 定稿前三语互查：有没有哪一版多出或少掉限定词、把「可能」写成「是」。

**已知的真实缺口与对策**
- 中文版第一人称密度曾低到 **0 / 千字**，而英文是 8.3。中文技术写作允许省略主语，但整篇零主语会
  把「个人实验记录」读成「器件手册」。**改写时必须保留英文的第一人称视角。**
- 中文正文里的**半角标点**是历史遗留：半角 `;` 要改成全角 `；`（相邻字符有 CJK 才算）。
- 荷兰文里 `niet X, maar Y` 这一类，很多是翻译时新引入的，英文原句并没有；**要回英文确认**。

## 10. 已知缺陷模式（历史上真实踩过）

| 缺陷 | 现象 | 检查方法 | 修法 |
|---|---|---|---|
| **`~~` 删除线** | 中文里出现 `5~~30mA`，Markdown 渲染成**删除线** | 全文搜 `~~` | 改成单个 `~`（本站区间惯例是单波浪号，如 `1~2m`、`¥10~30`） |
| **半角标点混入中文** | 中文正文里用半角 `;` | 搜相邻字符含 CJK 的半角标点 | `;` → `；`。**但先看语义**：见下一条 |
| **标题冒号误用分号** | `# 材料选择; 每一层…` 被机械改成 `# 材料选择；…`，而英文是 `Choosing Materials: …` | 对比中英标题，找中文用 `；` 而英文用 `:` 的地方 | 标题里的 `；` → **全角冒号 `：`** |
| **全角标点后多一个空格** | `不一样； 放了很久…` | 搜 `；` 后跟空格 | 删空格（中文全角标点后不加空格） |
| **中文标题与英文含义脱节** | 英文 `What I Built`，中文写 `项目目标` | 逐条对比中英标题 | 按 §3.3 的词表对齐 |
| **英文拼写混乱** | 同一文件里 colour/color 并存 | 搜英式拼写 | 按 §7 统一为美式 |
| **目录名与 translationKey 不一致** | `zoem-bike-bakfiets` 目录 vs `zoem-bike-cargo-box` key | 比对两者 | 目前三语都一致所以不坏，但新条目要避免 |
